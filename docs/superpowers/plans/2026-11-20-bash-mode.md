# `!` Bash 模式 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 輸入框開頭打 `!` 直接執行 shell 指令，結果顯示在畫面上，並把「指令＋輸出」附在使用者下一句送給模型。

**Architecture:** 從 `internal/tools/shell` 抽出 `Run`，讓 Bash 工具與 TUI 共用。TUI 新增 `bashmode.go`：在 `handleSubmit` 攔截 `!`，用 `tea.Cmd` 非同步執行，結果暫存在 `bashPending`，由 `startQueryCmd` 接在使用者文字前面（作法同 `/btw` 的 `btwPending`）。

**Tech Stack:** Go 1.26、`charm.land/bubbletea/v2`、`charm.land/lipgloss/v2`、`os/exec`。

**Spec:** `docs/superpowers/specs/2026-11-20-bash-mode-design.md`

## Global Constraints

- 依賴方向：TUI 可以 import `internal/tools/shell`，但**不可以** import `internal/bootstrap`。
- 逾時用 `shell.DefaultBashTimeoutMs`（120_000 ms）。送進脈絡的輸出上限是 **30,000 字元**（以 rune 計，不可切在 UTF-8 中間），截斷時加上註明。
- 脈絡格式：`<bash-input>cmd</bash-input>\n<bash-stdout>…</bash-stdout>\n<bash-stderr>…</bash-stderr>`。
- 不走權限決策鏈、不新增 API 呼叫、不改工具註冊與 schema（Cache-first：只在 turn 尾端注入）。
- 檔案 ≤800 行（`keys.go` 已有 677 行，新邏輯一律放 `bashmode.go`），函式 ≤80 行，導出符號要有 GoDoc，錯誤用 `fmt.Errorf("...: %w", err)`，I/O 函式第一個參數是 `context.Context`。
- TUI 的 UI 文字沿用既有的英文（例：`btwPendingHint`）。
- TUI 測試用「詞」做斷言，不比對完整字串。

## Review Focus

1. 只打 `!` 或 `!   `：直接忽略，不執行、不暫存，也不送給模型（Task 2 `TestBashSubmit_EmptyIgnored`）。
2. 下一句送出前連續跑多個 `!`：要依執行順序全部附上（Task 2 `TestBashPending_Accumulates`）。
3. 指令還在跑時就 `/clear`，或在 `/clear` 之後才回來的結果：要丟棄，不能復活到新對話（Task 2 `TestBashResult_StaleAfterClearDropped`）。
4. 模型正在回應時打 `!`，接著送出的那句被排進佇列：佇列送出時要附上輸出（`update.go:505/514` 也走 `startQueryCmd`，所以 Task 2 `TestBashPending_AttachedViaStartQuery` 已涵蓋）。
5. 超大或多位元組的輸出：截斷後仍是合法 UTF-8，並帶有截斷註明（Task 2 `TestFormatBashContext_TruncatesRunes`）。

### Task 2: TUI `!` 模式核心

**Files:**
- Create: `internal/tui/bashmode.go`
- Modify: `internal/tui/keys.go`（`handleSubmit` 在 `/btw` 之後分派；Esc 分支）、`internal/tui/cmds.go:66`（附加 pending）、`internal/tui/update.go`（`case bashResultMsg`；`ClearHistory` 清狀態）、`internal/tui/model.go`（`AppModel` 欄位）、`internal/tui/view.go:49`（hint）
- Test: `internal/tui/bashmode_test.go`

**Interfaces:**
- Consumes: `shell.Run`、`shell.RunResult`、`shell.DefaultBashTimeoutMs`（Task 1）。
- Produces（package-private）：
  ```go
  const bashContextLimit = 30_000
  type bashResultMsg struct { gen uint64; command string; res shell.RunResult; err error }
  // AppModel 新增欄位：bashPending []string; bashCancel context.CancelFunc; bashGen uint64
  func parseBang(text string) (command string, ok bool)          // "!" 開頭時 ok=true；command 已 trim
  func formatBashContext(command string, res shell.RunResult) string
  func (m AppModel) startBash(command string) (AppModel, tea.Cmd)
  func (m AppModel) onBashResult(msg bashResultMsg) (AppModel, tea.Cmd)
  func (m *AppModel) takeBashPending(userText string) string     // 以 "\n\n" 連接 pending 與 userText，然後清空 pending
  func (m AppModel) bashPendingHint() string
  func (m AppModel) cancelBash() AppModel
  ```

- [ ] **Step 1: 寫失敗的測試**（`bashmode_test.go`）：
  - `TestParseBang`：`"!ls"`→`("ls",true)`、`"!  git status "`→`("git status",true)`、`"ls"`→`ok=false`、`"!"`→`("",true)`。
  - `TestBashSubmit_EmptyIgnored`：送出 `"!  "` → 回傳的 cmd 是 nil，`bashPending` 為空，也沒有開始查詢（`isLoading` 為 false）。
  - `TestFormatBashContext`：含有 `<bash-input>ls</bash-input>`、`<bash-stdout>a</bash-stdout>`。stderr 為空時不輸出 `<bash-stderr>`。ExitCode≠0 時含有 `exit code 2` 這個詞。
  - `TestFormatBashContext_TruncatesRunes`：stdout 是 40,000 個 `"中"` → 結果 `utf8.ValidString`，stdout 區段的 rune 數 ≤30,000，而且含有 `truncated` 這個詞。
  - `TestBashResult_AppendsPendingAndDisplay`：`onBashResult` 之後 `bashPending` 長度為 1，`m.messages` 最後一則含有 `hi`。
  - `TestBashPending_Accumulates`：兩次結果 → `takeBashPending("q")` 依序包含兩段，結尾是 `q`，呼叫之後 pending 為空。
  - `TestBashPending_AttachedViaStartQuery`：有 pending 時呼叫 `startQueryCmd` → 送給 engine 的最後一則 user 訊息含有 `<bash-input>`（沿用 `btw_send_test.go` 的 fake engine 寫法）。
  - `TestBashResult_StaleAfterClearDropped`：startBash 之後執行 `/clear`（`ClearHistory`），再送入舊 gen 的 `bashResultMsg` → pending 與 messages 都沒有變化。
  - `TestBashEsc_CancelsRunning`：`bashCancel` 不為 nil 時按 Esc → 取消被呼叫，而且 `isLoading` 的查詢沒有被 abort；取消回來的結果（`Canceled`）會顯示含有 `canceled` 的訊息，但不加入 pending。
  - `TestBashEsc_DiscardsPending`：閒置且有 pending 時按 Esc → pending 被清空。
- [ ] **Step 2: 執行** `go test -race -run 'Bash|ParseBang' ./internal/tui/`，預期 FAIL（undefined）。
- [ ] **Step 3: 實作**：
  - `handleSubmit`：在 `/btw` 之後加上 `if cmd, ok := parseBang(text); ok { if cmd == "" { return m, nil }; return m.startBash(cmd) }`。不論模型是否在忙都立即執行，不排進佇列。
  - `startBash`：`bashGen++`，建立 cancelable ctx 並存成 `bashCancel`，把 `newUserMessage("! "+cmd)` 加進 `m.messages`，然後回傳一個呼叫 `shell.Run(ctx, m.appState.GetState().WorkingDir, cmd, DefaultBashTimeoutMs*ms)` 的 `tea.Cmd`，結果包成 `bashResultMsg`。
  - `onBashResult`：gen 和目前的 `bashGen` 不同就丟棄。相同時清掉 `bashCancel`。被取消的情況顯示 `command canceled`，不加入 pending。其他情況顯示 stdout/stderr（放在 code fence 裡，避免被當成 markdown 渲染），exit≠0 時另外顯示 `exit code N`，並且 `bashPending = append(..., formatBashContext(...))`。
  - Esc 分支（`keys.go:259` 的 btw 判斷之後、`isLoading` 之前）：有 `bashCancel` 就 `cancelBash()` 然後 return。閒置時，在清 `btwPending` 的同一段也一起清 `bashPending`。
  - `cmds.go:66`：在 `takeBTWPending` 之後呼叫 `userText = m.takeBashPending(userText)`。
  - `ClearHistory`：先 `cancelBash()`，再 `bashPending = nil`、`bashGen++`。
  - `bashPendingHint`：`"N shell output(s) will be attached to your next message · Esc to discard"`（muted 樣式），在 `view.go:49` 和 btw hint 並列顯示。
- [ ] **Step 4: 執行** `go test -race ./internal/tui/`，預期全部 PASS。
